# 멀티 롤 회의 — 검수 이력 DB 사용량·관리 (아젠다)

**일자**: 2026-02-13  
**안건**: MVP 소규모 테스트만으로 검수 이력(inspection_runs / inspection_findings)이 100건을 넘어감. DB 사용량·관리 부담 대응 방안.

---

## 1. 현황 공유

### 1.1 데이터 규모

- **inspection_findings**: MVP 테스트 수준에서 이미 **100건 이상** (예: run 1회당 1~10건 적발).
- **inspection_runs**: 검수 실행 1회 = 1행. 테스트/실사용이 쌓일수록 선형 증가.
- **특징**:
  - 동일 risk_code·유사 matched_text(예: "할인", "이벤트")가 **키워드 룰별·run별로 중복** 저장됨.
  - explanation/suggestion 텍스트가 row마다 반복 저장 (정규화되지 않음).
  - Aiven 등 클라우드 DB는 **스토리지·백업 비용**이 건수/용량에 비례할 수 있음.

### 1.2 우려 사항

- **용량**: 이력 무제한 저장 시 실서비스에서 **월 수천~수만 건** 가능 → 스토리지·비용 증가.
- **관리**: 오래된 데이터 정리·아카이빙·삭제 정책이 없으면 **운영 부담**만 커짐.
- **성능**: 이력 목록/상세 조회 시 **페이지네이션 없이 전량 조회**하면 구간에 따라 지연 가능.

---

## 2. 역할별 진단·입장

### 역할 1: 기획/운영

- **진단**: 검수 이력은 "언제·무엇을 검수했는지" 감사·재검토용으로 필요하나, **전 기간 전 건 보관**이 필수는 아님.
- **입장**:  
  - **보존 기간 정책**: 예) 최근 90일(또는 1년)만 상세 보관, 그 이전은 요약만 보관 또는 삭제.  
  - **용도별 구분**: "개인 이력 조회"는 최근 N건, "관리자/감사"는 기간·워크스페이스별 집계·샘플만 유지하는 방식 검토.  
- **제안**: 보존 기간·최대 건수(예: 사용자당 최근 500 run)를 **정책으로 정한 뒤**, 스케줄 삭제/아카이빙으로 DB 부담 완화.

---

### 역할 2: 백엔드/API

- **진단**: 현재 **모든 검수 실행에 대해** run 1건 + findings N건을 **무조건 INSERT**. 삭제/아카이빙 로직 없음.
- **입장**:  
  - 저장은 "감사·이력" 목적이므로 **당장 저장 방식을 바꾸기보다**, **주기적 정리(삭제/아카이빙)** 로 구간을 나누는 쪽이 안전.  
  - 이력 API는 이미 **페이지네이션**(page/limit) 지원 시, 오래된 데이터가 많아도 목록 조회 부하는 제한 가능.  
- **제안**:  
  - **보존 기간 도입**: 설정(또는 .env)으로 "N일 이전 run/findings 삭제" 스크립트 또는 스케줄 작업.  
  - (선택) **상세 저장 제한**: run당 findings 상위 M건만 저장, 나머지는 요약만 등 — 요구가 있으면 도입.

---

### 역할 3: DB/운영

- **진단**: inspection_findings는 **run_id + risk_code + matched_text + explanation + suggestion** 등으로 row가 길고, 건수만 많아져도 **디스크·백업**이 커짐.
- **입장**:  
  - **테이블 구조 변경**보다 **데이터 수명 주기(Lifecycle)** 부여가 우선.  
  - 오래된 데이터 **삭제** 또는 **아카이브 테이블/파일로 이관** 후 본 테이블에서는 삭제.  
- **제안**:  
  - **정책**: "검수 이력 보존 기간 90일(또는 180일)".  
  - **실행**: 주기적(예: 매일/매주)으로 `created_at < (NOW() - N일)` 인 run 삭제, CASCADE로 findings 함께 삭제.  
  - (선택) 삭제 전 **CSV/백업 export** 후 외부 스토리지 보관.

---

### 역할 4: 룰엔진/검수 로직

- **진단**: 엔진은 "검수 1회 실행 시 findings N건 반환"만 책임. **저장 건수**는 API/핸들러·정책 이슈.
- **입장**:  
  - **중복 감소**: 같은 문구에서 "할인""이벤트"를 **키워드 룰 2건**이 각각 잡으면 findings 2건. 필요 시 **동일 run 내 risk_code+matched_text 중복 제거** 또는 **룰 단위 요약** 저장은 기획/백엔드 검토.  
  - **저장 단위**: "run 1 + findings N" 유지해도 되고, "run 1 + findings 요약(risk_code별 1건)" 등으로 줄이는 건 정책 선택.  
- **제안**: 우선 **보존 기간·주기 삭제**로 용량을 관리하고, "finding당 row 줄이기"는 요구가 있을 때 설계.

---

### 역할 5: 프론트엔드

- **진단**: 이력 목록/상세는 **API 응답**만 표시. 데이터가 많으면 **페이지네이션·로딩**만 잘 되면 됨.
- **입장**:  
  - **최근 N건만** 보여주는 정책이면, API가 이미 page/limit 지원 시 프론트는 그대로 사용.  
  - "전체 이력"을 요구하지 않으면, 오래된 데이터 삭제에 따른 UX 변경 최소.  
- **제안**: 이력 화면에서 "최근 90일" 등 필터/안내만 추가해도 정책 전달 가능.

---

- **단기(MVP)**  
  - **보존 기간**: 예) **90일**. 90일 이전 `inspection_runs` (및 CASCADE findings) **주기 삭제** 스크립트 도입.  
  - **저장 방식**: 현재처럼 run 1 + findings N건 유지. (중복 축소는 별도 이슈로.)

  - 필요 시 삭제 전 **아카이브 export** 옵션 추가.

# Part II. 멀티 롤 회의 — 사용자 광고 데이터 자산화 (아젠다)

**일자**: 2026-02-13  
**안건**: 사용자가 검수에 넣는 **광고 문구·검수 결과**를 AdSafe의 **핵심 자산**으로 활용할 수 있는 방안. (이력 DB 관리와 연계해 정책·개인정보·기술 설계.)

---

## II-1. 배경·가치

### II-1.1 왜 "광고 데이터"가 자산인가

- **실제 업계 문구**: 사용자가 입력한 문구는 **실제 의료·이벤트 광고** 또는 그에 가까운 텍스트. 시중 표현·트렌드·리스크 패턴을 반영.
- **검수 결과와 쌍**: "문구 + 적발된 risk_code·matched_text·레벨"이 함께 쌓이면 **룰 개선·검증**, **통계·트렌드 분석**, **AI/모델 학습** 등에 활용 가능.
- **경쟁 차별화**: 축적된 데이터로 "어떤 표현이 얼마나 자주 적발되는지", "업종별 리스크 분포" 등을 제공하면 **AdSafe만의 인사이트**가 됨.

### II-1.2 현재 저장 상태

- **inspection_runs**: ad_type, ad_title, **normalized_text**(전처리된 문구), risk_summary_level, total_findings, created_by, workspace_id 등.
- **inspection_findings**: risk_code, matched_text, explanation, suggestion, rule_id 등.
- **개인정보 연계**: created_by(user_id)로 **누가** 검수했는지 연결 가능. 문구 자체에 개인·기관 정보가 포함될 수 있음.

---

## II-2. 역할별 진단·입장 (광고 데이터 자산화)

### 역할 1: 기획/제품

- **진단**: 사용자 광고 데이터는 **서비스 품질 향상·인사이트 제품화**의 원료이나, **수집 목적·이용 범위**를 명확히 하지 않으면 신뢰 하락·규제 리스크.
- **입장**:  
  - **이용 목적 정의**: (1) 검수 이력·재검토 (2) 룰/엔진 개선 (3) 익명 집계·트렌드 리포트 (4) AI/학습 (선택). 목적별 **동의·옵트인** 구분.  
  - **자산화 단계**: 1단계 "이력만 보관", 2단계 "익명 집계로 통계", 3단계 "동의 구간만 학습/제품 활용".  
- **제안**: 약관·개인정보처리방침에 "검수 문구·결과의 보관 및 익명 통계·품질 개선 활용" 조항 추가. **자산 활용은 기본 익명화·옵트아웃(또는 옵트인)** 전제.

---

### 역할 2: 백엔드/API

- **진단**: 현재는 "검수 시 무조건 run+findings 저장". **용도 플래그**(이력만 / 통계 활용 / 학습 허용)나 **사용자 동의 플래그**는 없음.
- **입장**:  
  - 자산화를 **저장 구조부터** 나누기보다, **정책(보존 기간·용도)** 확정 후 "용도별 보관 여부" 컬럼 또는 별도 집계 파이프라인 도입 검토.  
  - **익명 집계**: 개인 식별 제거 후 집계 테이블/뷰 또는 배치로 "risk_code별 건수", "matched_text 샘플(익명)" 등 생성 가능.  
- **제안**:  
  - **1단계**: 현 구조 유지, **약관/정책**으로 "익명화·집계·품질 개선에 활용할 수 있음" 명시.  
  - **2단계**: (선택) `inspection_runs`에 `allow_analytics` 또는 `data_usage_consent` 같은 플래그 추가, 동의한 건만 통계/학습 파이프라인에 포함.

---

### 역할 3: DB/운영·개인정보

- **진단**: **문구+user_id**가 쌓이면 "누가 어떤 문구를 검수했는지" 복원 가능. 개인정보보호법·GDPR 등에서 **목적 명시·최소 수집·보존 기간** 필요.
- **입장**:  
  - **자산화**와 **개인정보 최소화**를 함께 설계. "통계/학습용"은 **user_id·workspace_id 제거** 또는 **집계만** 보관.  
  - **보존 기간**: Part I과 동일하게 "이력 보존 N일" 적용. "자산(집계/샘플)"은 **익명·비식별** 후 별도 보존 기간 정책.  
- **제안**:  
  - **정책 문서**: "검수 데이터 수집·보존·이용 목적" 한 곳에 정리.  
  - **익명 집계**: 개인 식별자 제거, 문구는 필요 시 일부 마스킹·요약만 저장.  
  - **삭제 요청**: 회원 탈퇴·동의 철회 시 해당 사용자 run/findings 삭제 또는 비식별 처리 절차.

---

### 역할 4: 룰엔진/데이터 활용

- **진단**: **실제 적발 패턴**이 쌓이면 "어떤 룰이 과적발/과소적발인지", "새 패턴 후보" 발견에 유리.
- **입장**:  
  - **자산** = (문구, 적발 결과) **쌍**. 보관 시 **rule_id·risk_code·matched_text**가 있으면 룰 성능 분석·튜닝에 바로 사용 가능.  
  - **학습용**: 미래에 ML 모델을 쓸 경우, **동의된·익명화된** 문구+라벨(risk) 데이터셋이 필요.  
- **제안**:  
  - 단기: 이력 보존 기간 내 데이터로 **내부 룰 성능 리포트**(risk_code별 건수, 샘플 리뷰)만 진행.  
  - 중기: "통계/품질 개선 동의" 구간만 **익명 집계 테이블** 또는 샘플 export로 룰 개선·학습에 활용.

---

### 역할 5: 법무/준법·개인정보

- **진단**: 사용자 생성 광고 문구는 **개인정보에 해당할 수 있음**(작성자·기관 추정 가능 시). 수집·이용·제3자 제공·보존 기간을 **고지·동의**해야 함.
- **입장**:  
  - **자산화** = "이력" 외에 **통계·연구·제품 개선·AI 학습** 등으로 쓰는 경우, **이용 목적**을 약관/개인정보처리방침에 넣고, 필요 시 **동의(옵트인)** 또는 **옵트아웃** 절차 도입.  
  - **익명/비식별** 기준 명확화: 어떤 항목을 제거·변형하면 "개인 식별 불가"로 볼지 정의.  
- **제안**:  
  - "검수 문구·결과는 서비스 제공·이력 조회·익명 통계·서비스 품질 개선에 사용될 수 있으며, 개인을 식별할 수 없는 형태로만 통계에 활용합니다" 등 문구 검토.  
  - 자산화 범위가 "내부 통계"를 넘어 **제3자 제공·학습 데이터 판매** 등이 되면 별도 동의·계약 검토.

| 4 | **자산 보관 단위** | run 단위 유지 / 집계·샘플만 별도 테이블 | Part I 보존 기간과 연계 |
