## 2. 역할별 진단·입장

### 역할 1: 기획/제품

- **진단**: 구조 정리는 **온보딩·유지보수 비용**과 직결됨. 과한 변경은 리스크·테스트 부담을 키울 수 있음.
- **입장**:  
  - **점진적 정리**를 권장. “한 번에 대이동”보다 **규칙 정한 뒤 신규부터 적용**·기존은 필요 시 단계 이전.  
  - **문서화 우선**: “어디에 무엇을 둘지” 규칙을 `docs/` 또는 루트 CONTRIBUTING/README에 명시.  
- **제안**:  
  - 1단계: **현 구조 유지 + 명명·배치 규칙 문서화** (신규 파일만 규칙 적용).  
  - 2단계: 이슈/리팩터 시점에 **폴더 이동** (예: 정적 자산 → `assets/`, 배포 설정 → `config/`).

---

### 역할 2: 백엔드/API

- **진단**: `api/` 안에 **PHP(실제 API)·Node(시드/도구/레거시 서버)·.env·ca.pem·실행 가이드**가 함께 있어, “API 코드”와 “설정·도구” 경계가 불명확함. **Node 잔존 이유·처리**는 § Part II 참고.
- **입장**:  
  - **API 진입점**은 `api/index.php`·`api/routes.php`·`handlers/`·`engine/` 로 이미 역할이 나뉘어 있어, **당장 폴더 분리보다** `api/README.md`·`실행_순서_가이드.md`로 “무엇이 어디에 있는지” 정리하는 것이 먼저.  
  - **설정·인증서**: 실무에서는 `api/config/`(설정만), `api/certs/` 또는 루트 `config/` 로 빼는 경우가 많음.  
- **제안**:  
  - **단기**: `api/` 내부는 유지, **문서**로 디렉토리 맵 정리. `.env.example`·`ca.pem` 위치는 README에 명시.  
  - **중기**: `api/.env`·`api/ca.pem` → 루트 `config/`(또는 `api/config/`) 로 옮길지 회의 결정. (PHP include 경로·Apache 설정 변경 필요.)

---

### 역할 3: 프론트엔드

- **진단**: 루트에 HTML이 많고, `js/`·`styles.css`·`main.js` 가 분리되어 있어 **진입점·자산**이 한눈에 들어오지 않음.
- **입장**:  
  - 실무에서는 **public/** 또는 **src/** 아래에 `index.html`, `pages/`(또는 화면별 폴더), `assets/css/`, `assets/js/` 구조를 많이 씀.  
  - 다만 **XAMPP 직접 서빙** 전제라면, Apache DocumentRoot가 `Adsafe/` 이므로 **루트 이동 시 URL·링크 전면 수정** 필요.  
- **제안**:  
  - **Option A (최소 변경)**: 루트 구조 유지, **규칙만 정리** — “새 HTML은 `pages/` 또는 루트, 새 스크립트는 `js/` by 기능”.  
  - **Option B (점진 이전)**: `public/` 폴더를 만들고, `index.html`·`login.html` 등 진입점만 `public/` 로 옮긴 뒤 Apache 가상호스트 또는 Rewrite로 `/` → `public/` 매핑. (빌드 도구 없이 정적만 있을 때 선택.)  
  - **Option C (전면 재구성)**: `frontend/` 또는 `public/` 아래에 `css/`, `js/`, `admin/`, 페이지별 HTML 재배치. URL 변경·테스트 부담 큼.

---

### 역할 4: DB/운영

- **진단**: DB 스키마·시드·연결 가이드는 이미 `docs/sql/` 에 있어 **문서 측면**은 정리됨. 코드 측에서는 `api/` 가 DB 접근의 진입점.
- **입장**:  
  - 폴더 구조보다 **환경별 설정 분리**가 중요. `.env` 위치가 바뀌면 **배포 스크립트·CI**에서 경로 수정 필요.  
  - **마이그레이션·시드 스크립트**는 `api/scripts/` 또는 전사 공통 `scripts/` 중 일관된 한 곳에 두는 것이 유지보수에 유리.  
- **제안**:  
  - 구조 정리 시 **DB 연결·시드 실행 경로**를 문서화하고, 변경 시 배포 체크리스트에 “.env·시드 경로” 항목 추가.  
  - `docs/sql/` 은 유지.

---

### 역할 5: 배포/인프라(또는 풀스택)

- **진단**: `apache-api-proxy.conf` 가 루트에 있고, XAMPP 기준으로 PHP API는 `api/` 에서 직접 실행됨. **배포·환경 설정**이 프로젝트 루트와 섞여 있음.
- **입장**:  
  - 실무에서는 **config/** 또는 **deploy/** 에 Apache/Nginx 설정, 환경별 설정 템플릿을 두는 경우가 많음.  
  - **scripts/** 는 Git·빌드·동기화용으로 적절하나, “배포 전용”이면 `deploy/` 또는 `scripts/deploy/` 로 구분 가능.  
- **제안**:  
  - **1단계**: 루트에 `config/` 생성, `apache-api-proxy.conf` 를 `config/apache-api-proxy.conf` 로 이동 후 배포 문서에 경로 명시. (또는 “참고용으로만 두고 실제 서버 설정은 별도 저장” 정책.)  
  - **2단계**: `.env.example` 을 루트 `config/.env.example` 또는 `api/.env.example` 중 **한 곳**으로 통일하고, “실제 .env는 api/ 또는 config/” 를 문서에 명시.

# Part II. Node 잔존 이유 및 처리 방안 (회의 안건)

**일자**: 2026-02-13  
**안건**: `api/` 내 Node(Express·스크립트)가 **왜 남아 있는지**, **실행 API는 PHP로 이전된 뒤** 잔존 Node를 **어떻게 처리할지** 결정.

> **별도 회의**: 운영 스택 정책(Node·Express 미사용, PHP + 필요 시 Python + OpenAPI) 및 제거·이전 구현은 **전용 아젠다**에서 다룹니다.  
> → **`docs/meetings/agenda/Node_Express_잔존_정책_아젠다.md`** (회의 후 Cursor 플랜 모드로 구현 예정)

---

## II-1. Node를 쓰게 된 이유 (역사적 맥락)

- **초기 구성**: AdSafe API는 **Node + Express** 로 구축됨. `server.js`, `routes/inspect.js`, `routes/inspection-history.js`, `lib/inspection-engine.js`, `lib/rules-data.js`, `lib/normalize.js`, `config/db.js` 로 검수·이력·DB 연동을 제공.
- **PHP 도입**: XAMPP 환경에서 **Apache만으로 API 제공**하려고 PHP 진입점(`index.php`, `routes.php`, `handlers/`, `engine/`)을 추가. 검수 실행은 `POST /api/inspect` → **PHP**가 담당하도록 정리됨. (CTO 보고서: 브라우저 JS 검수 엔진 제거·이벤트 룰 DB 이전 시 **서버는 PHP만** 사용.)
- **Node 잔존 이유 요약**  
  - **과거**: API 서버가 Node였고, 배포 옵션으로 Apache 프록시 → Node(3000 포트) 구성이 있었음.  
  - **현재**: 실제 **런타임 API는 PHP**. Node는 **도구·초기화 전용**으로만 사용됨.  
    - **시드**: `npm run seed` → `scripts/seed.js` (workspaces, users, risk_taxonomy, quizzes 등 초기 데이터). Node만으로 DB 접속·`api/lib/rules-data.js`·`js/adusafe-questions.js` 로드.  
    - **진단**: `scripts/check-db.js` (DB 연결·.env·SSL 확인).  
    - **테스트**: `scripts/test-inspect-save.js` (검수 저장 연동 확인).  
  - **server.js**: Express 서버는 **PHP 사용 시 기동하지 않음**. 레거시·대안 실행용으로만 존재.

---

## II-2. 현재 Node 잔존 목록

| 구분 | 경로 | 용도 | PHP 대체 여부 |
|------|------|------|----------------|
| **API 서버** | `api/server.js` | Express 검수·이력 API | ✅ PHP로 대체됨 (사용 안 함) |
| **라우트** | `api/routes/inspect.js`, `inspection-history.js` | Node API 엔드포인트 | ✅ PHP handlers로 대체 |
| **엔진/룰** | `api/lib/inspection-engine.js`, `rules-data.js`, `normalize.js` | 검수·룰 로직 | ✅ PHP `engine/` 로 대체 |
| **DB 연결** | `api/config/db.js` | Node용 MySQL 풀 | 시드·스크립트에서만 사용 |
| **시드** | `api/scripts/seed.js` | 초기 데이터 INSERT | ❌ PHP 동일 기능 없음 |
| **도구** | `api/scripts/check-db.js`, `test-inspect-save.js` | DB 진단·저장 테스트 | ❌ PHP 스크립트 없음 |
| **패키지** | `api/package.json`, `package-lock.json`, `node_modules/` | npm 의존성 | seed·check-db 등에 필요 |

---

## II-3. 역할별 진단·입장 (Node 처리)

### 역할 1: 기획/제품

- **진단**: **Node 런타임 의존**이 있으면 “XAMPP만 켜면 된다”는 설명과 어긋남. 반면 시드·도구를 PHP로 옮기면 개발·유지보수 공수가 듦.
- **입장**:  
  - **목표 명확화**: “운영 시 Node 불필요” vs “개발/초기 설정 시에만 Node 사용” 중 하나를 정책으로 정함.  
  - **문서화**: “API는 PHP, Node는 시드·진단용(선택)” 등으로 README·실행 가이드에 명시.  
- **제안**:  
  - **Option A**: Node **유지** — 시드·check-db·test 스크립트만 사용, server.js는 “레거시/참고”로 문서 표기.  
  - **Option B**: Node **축소** — server.js·routes 제거, `api/scripts/` + `config/db.js` + `lib/rules-data.js`(시드용)만 유지.  
  - **Option C**: Node **제거** — 시드·진단을 PHP 또는 순수 SQL 스크립트로 이전 후 `api/` 에서 Node 의존 제거.

---

### 역할 2: 백엔드/API

- **진단**: **실제 검수·이력 API는 100% PHP**. Node lib(검수 엔진)은 시드가 `ADU_RULES` 등을 참조할 때만 사용됨. 중복 유지보수(룰 로직이 PHP와 Node 양쪽에 있으면 안 됨)는 이미 PHP 쪽으로 정리된 상태.
- **입장**:  
  - **server.js·routes**: 사용하지 않으면 **삭제** 또는 `api/legacy/` 등으로 이동 후 “실행하지 않음” 문서화.  
  - **시드**: Node 유지 시 `api/scripts/`·`config/db.js`·`lib/rules-data.js`(및 시드 전용 최소 코드)만 두고, **검수 엔진 로직**은 PHP만 참조하도록 명시.  
  - **시드 PHP 이전**: 가능하나, risk_taxonomy·quizzes 등 로직을 PHP로 옮기고 `js/adusafe-questions.js` 로드 방식을 PHP에서 처리해야 함. 공수 대비 이득은 “Node 제거”일 때 큼.
- **제안**:  
  - **단기**: server.js·routes 삭제 또는 legacy 이동, **README에 “실행 API는 PHP, Node는 seed/check-db 전용”** 명시.  
  - **중기**: “Node 완전 제거” 결정 시 시드 PHP 스크립트(또는 SQL만) 설계.

---

### 역할 3: DB/운영

- **진단**: 시드 실행이 **Node 필수**이면, 배포·CI에서 `node`, `npm install`, `npm run seed` 가 필요. PHP만 있는 서버에서는 Node 설치 부담이 생김.
- **입장**:  
  - **Node 유지**: 개발·로컬에서는 `npm run seed`로 간단. 운영에서도 “초기 1회”만 쓰면 Node 한 번 설치로 가능.  
  - **Node 제거**: 시드를 **SQL 파일 + 수동 실행** 또는 **PHP CLI 스크립트**로 바꾸면, 런타임은 PHP만 필요. 다만 risk_taxonomy·quizzes 등 동적 생성 로직을 SQL 또는 PHP로 다시 짜야 함.
- **제안**:  
  - 시드 데이터가 **고정**이면 `docs/sql/` 에 INSERT 위주 SQL로 두고, “Node 시드는 선택, SQL 직접 실행으로 대체 가능” 문서화.  
  - 시드가 **ADU_RULES·ADU_QUESTIONS 기반 동적**이면, Node 유지 vs PHP 시드 스크립트 도입 비용을 비교해 결정.

---

### 역할 4: 배포/인프라

- **진단**: `실행_순서_가이드.md` 에 “API는 PHP”, “(선택) npm run seed”라고 되어 있음. **Node가 없어도 동작**하도록 하려면 시드·도구를 PHP 또는 SQL로 대체해야 함.
- **입장**:  
  - **최소 배포**: Apache + PHP + MySQL만 필요하게 하려면 Node 제거가 유리.  
  - **개발 편의**: check-db, test-inspect-save 등 Node 스크립트가 있으면 로컬 진단이 빠름. 제거 시 동일 기능의 PHP 또는 셸 스크립트 대안 필요.
- **제안**:  
  - “운영 배포에서 Node 미사용”을 목표로 하면 **Node 제거 + 시드/도구 PHP·SQL 이전** 로드맵 수립.  
  - “개발용 Node 유지”로 하면 **server.js 제거만** 하고, package.json scripts는 seed·check-db·test만 유지.
